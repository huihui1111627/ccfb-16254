# QUIC CID Load Balancer Simulator

一个用 Go 标准库实现的本地演练系统：四层负载均衡不再只按外层源 `IP:端口` 哈希，而是解析 QUIC 包头并按 **Connection ID 中认证编码的后端身份** 路由。

页面模拟一批手机用户在 Wi‑Fi / 4G 之间切换，穿插后端扩容、缩容排空、LB 扩容/缩容和重启，并与传统源地址哈希做同种子、同丢包/乱序输入的逐项对比。

## 运行

```bash
go run .
# 等价入口：go run ./cmd/cidlb
# 打开 http://127.0.0.1:8080
```

常用参数：

```bash
go run . -addr 127.0.0.1:9090 -users 128 -duration-sec 180 -seed 42
```

运行测试：

```bash
go test ./...
go vet ./...
```

仪表板支持调整用户数和随机种子后重新模拟，也提供 JSON API：

- `GET /api/state`：汇总指标、用户、迁移、后端、LB、事件、负载时间序列。
- `GET /api/packets?mode=cid|old&trace=<session-id>`：某个逻辑连接的逐包记录。
- `POST /api/rerun?users=96&seed=20261125`：重新生成确定性场景。

## 核心结论如何验证

默认种子下可以看到：

- CID 模式的迁移保活率为 `549/549 (100%)`，已建立连接的错误路由包为 `0`。
- 传统源地址哈希只有少量迁移恰好哈希回同一后端；大量包被打到陌生后端，触发无状态重置和重新握手。
- CID 模式下，同一用户的会话条在后端泳道中始终停留在同一行；传统模式会出现红色错误段和新的握手代数。
- 伪造或用错误密钥生成的 CID 会在 HMAC 校验阶段被拒绝，不能把后端身份改成攻击者指定值。
- 多个 LB 实例不共享连接表。ECMP 可能在切网或实例变更后把包送到另一个 LB，但任何实例都能用同一共享密钥从 CID 解出相同后端。
- 缩容后端先进入 `draining`：不接收新连接，但老 CID 仍路由到它；最后一条老连接结束后才摘除。

> 传统哈希模式的后端包量有时看起来同样均匀，甚至统计 CV 更低：这是因为每次切网/扩缩容把连接打断并重新哈希，代价是连接迁移失败、重握手和上传失败。CID 模式优先保证连接亲和，长期连接分布会保留真实会话长度带来的倾斜；页面同时给出 CV 和 Jain 公平性。

## CID 设计

固定使用 QUIC 允许的 20 字节 DCID，短包头因此可以按约定长度直接截取，不需要长度字段：

```text
0       1          8            12               20
+-------+----------+------------+-----------------+
| keyID | nonce(7) | backend(4) | HMAC-SHA256/8B  |
+-------+----------+------------+-----------------+
```

- `backend` 是后端数字身份，使用 AES-CTR 加密，线上没有明文后端编号。
- `keyID` 只表示密钥代次，不表示后端。
- 前 12 字节使用 HMAC-SHA256 计算并截断 8 字节；LB 先做常量时间 MAC 比较，通过后才解密。
- 加密密钥和 MAC 密钥由共享 secret 分别派生。
- 不同 nonce 使同一后端生成的 CID 看起来完全不同。

代码：`internal/quicwire/cid.go`。

## QUIC 包头处理

`internal/quicwire/header.go` 按 RFC 9000 的关键格式构造和解析：

- **长包头**：Header Form、版本、DCID Length/DCID、SCID Length/SCID，并区分 Initial / Handshake / 0-RTT / Retry。
- **短包头（1-RTT）**：Header Form 为 0，后面没有 DCID 长度；按部署约定的 `quicwire.CIDLength = 20` 读取。
- **版本协商包**：Version 为 0，CID 后是支持的版本列表，单独分类和计数，不建立连接状态。
- **无状态重置包**：没有独立包类型；按包尾最后 16 字节 reset token 识别。传统哈希把包打到不认识连接的后端时会生成这类记录。

这里不实现完整 QUIC 加密、ACK、拥塞控制或 HTTP/3 状态机；握手和包头字段是真实格式，数据传输、视频卡顿和上传结果是可解释的简化模型。

## 模拟结构

```text
main.go               根目录便捷入口
cmd/cidlb             同一服务的 cmd 入口
internal/cli          命令行参数和 HTTP 生命周期
internal/quicwire     CID 安全编码 + QUIC 包头构造/解析
internal/sim          确定性用户、网络、流量、扩缩容和双模式路由模拟
internal/web          embed 静态仪表板和 JSON API
```

同一个确定性 `Scenario` 同时喂给两种模式，因此丢包、乱序、地址变化和运维事件完全一致：

1. 生成 96 个手机用户，每个用户在 Wi‑Fi 和 4G 地址间多次切换。
2. 生成有限生命周期的 QUIC 会话和 Initial / Handshake / 数据包。
3. 用带雪崩最终化的 rendezvous hash 为初始 DCID 选择新连接后端。
4. 后端为自己的身份签发认证 CID。
5. 每个包经过外层五元组 ECMP 选择 LB；LB 解析包头并决定路由。
6. CID 模式按认证 CID 路由；传统模式故意只按外层源地址键做 rendezvous hash。
7. 传统模式遇到陌生后端时记录错路包、stateless reset、重握手、卡顿和上传失败。
8. 聚合迁移、后端负载、连接数时间序列和逐包 trace。

## 页面能看什么

- 顶部 KPI：保活率、错路包、重握手/卡顿、上传失败、CV/Jain、伪造 CID 拦截。
- 左侧手机用户列表：每个用户的切网次数和老路径断连次数。
- 迁移详情：旧/新 `IP:端口`、网络类型、ECMP 前后 LB、CID 与老哈希的后端轨迹。
- 后端泳道：每个用户的每条 CID 连接/老路径握手代数落在哪台后端；叠加用户切网线和运维事件线。
- 逐包表：包头类型、源地址、LB、期望/实际后端、丢包、乱序、重置和错误原因。
- 扩缩容时间线：每次扩容、draining、排空完成、LB 重启和 ECMP 成员变化。
- 地址轨迹：每个用户每次 Wi‑Fi ↔ 4G 的地址变化和当时两种路由结果。
- 后端负载：包量条、份额、CV/Jain，以及 2 秒桶的包量/连接数热力图。
- 安全与协议：CID 字节布局、同一后端的不同 CID 样本、伪造测试和四类包头处理说明。

## 本地限制

- 所有 IP、后端和密钥都是本地模拟值；不要把演示 secret 用于生产。
- CID 布局是一个适合本演练的 QUIC-LB 风格方案，并非完整实现 QUIC-LB 规范。
- ECMP 用确定性五元组哈希模拟，不运行真实路由器。
- 视频卡顿用固定重握手恢复窗口近似，不解码实际视频流。
